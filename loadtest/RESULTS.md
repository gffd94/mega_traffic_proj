# 재고 차감 방식 비교 결과

`loadtest/stock-deduction.js`로 5가지 재고 차감 방식(none, atomic, pessimistic, optimistic, redisson)을 같은 조건에서 측정한 결과다.
원본 결과는 `loadtest/results/{방식}-{시나리오}-{시각}.json` 30개(5방식 × 2시나리오 × 3회)다.

## 측정 조건

| 항목 | 값 |
|---|---|
| 측정일 | 2026-10-12 |
| 기기 | Windows 11 Pro 노트북, Intel Core i5-1335U (10코어 / 12스레드), RAM 32GB |
| 배치 | k6, Spring Boot 앱, Docker(MySQL·Redis·RabbitMQ)가 모두 같은 기기에서 실행됨 (CPU를 서로 나눠 씀) |
| Docker | Docker Desktop 29.8.1 (WSL2), 컨테이너에 CPU 12개 / 메모리 약 15.5GB 할당 |
| 런타임 | Java 21.0.12, Spring Boot 3.5.16, Redisson 3.52.0, MySQL 8.4, Redis 7.4 |
| 커넥션 풀 | HikariCP 기본값 (최대 10) |
| Tomcat | 작업 스레드 최대 200 (기본값), **`accept-count` 1000** (기본값 100에서 변경, 아래 [트러블슈팅](#트러블슈팅) 참고) |
| k6 | v2.2.0 |
| 시나리오 A | 재고 100인 상품, VU 200명이 각자 정확히 1번 요청 (quantity 1) |
| 시나리오 B | 재고 100000인 상품, VU 100명이 30초 동안 쉬지 않고 요청 (quantity 1) |
| 반복 | none → atomic → pessimistic → optimistic → redisson 순서로 한 바퀴씩 3바퀴, 바퀴마다 A와 B를 모두 실행 |
| 예열 | 앱 기동 후 측정 전에 atomic A를 1번 실행하고 결과는 버림 |
| 앱 재시작 | 측정 중에는 앱을 재시작하지 않음 |
| 방식별 설정 | optimistic: 충돌 시 최대 3번 재시도 (재시도 사이 대기 없음), redisson: 락 대기 최대 5초 |

## 결과

- 표의 값은 3번 측정의 **중앙값**이다. 항목마다 따로 중앙값을 구하므로, 한 행의 값들이 서로 다른 회차에서 왔을 수 있다. 그래서 B의 `성공 + 503`이 `총 요청`과 딱 맞지 않을 수 있다.
- 판정 ①은 "처음 재고 − 성공 수 = 남은 재고", ②는 "남은 재고 ≥ 0"이다. 판정은 중앙값을 내지 않고 3회 결과를 그대로 적었다.
- 응답 시간은 밀리초(ms) 단위이며, 차감 요청만 집계했다.
- ⚠ 표시: 3회 값의 차이가 크다는 뜻이다. 기준은 (최댓값 − 최솟값) ÷ 중앙값 ≥ 30%다. 3회의 실제 값은 [값이 흔들린 항목](#값이-흔들린-항목)에 있다.

### 시나리오 A: 한정 수량 쟁탈 (재고 100, VU 200 × 1회)

| 방식 | 성공 | 409 | 503 | 그 외 (연결 실패) | 남은 재고 | 판정 ① | 판정 ② | avg | p95 | p99 |
|---|---|---|---|---|---|---|---|---|---|---|
| none | 200 | 0 | 0 | 0 (0) | 80 | FAIL ×3 | PASS ×3 | 405 | 757 | 787 |
| atomic | 100 | 100 | 0 | 0 (0) | 0 | PASS ×3 | PASS ×3 | 377 | 597 | 610 |
| pessimistic | 100 | 100 | 0 | 0 (0) | 0 | PASS ×3 | PASS ×3 | 435 ⚠ | 617 ⚠ | 623 ⚠ |
| optimistic | 70 | 0 | 130 | 0 (0) | 30 | PASS ×3 | PASS ×3 | 756 | 991 | 1001 |
| redisson | 100 | 100 | 0 | 0 (0) | 0 | PASS ×3 | PASS ×3 | 958 ⚠ | 1467 ⚠ | 1503 ⚠ |

- none은 3회 모두 200건이 성공했는데도 재고가 80개 남았다. 기대값은 −100이다. 실제로 반영된 차감은 20건뿐이다.
- optimistic은 재고가 30개 남았는데도 130건에 503(충돌 재시도 초과)을 돌려줬다. 3회 값은 성공 71/70/70, 503 129/130/130이다.

### 시나리오 B: 지속 부하 (재고 100000, VU 100 × 30초)

| 방식 | 총 요청 | 성공 | 409 | 503 | 그 외 | 판정 ① | 판정 ② | RPS | avg | p95 | p99 |
|---|---|---|---|---|---|---|---|---|---|---|---|
| none | 7501 | 7501 | 0 | 0 | 0 | FAIL ×3 | PASS ×3 | 246.7 | 403 | 450 | 502 |
| atomic | 7648 | 7648 | 0 | 0 | 0 | PASS ×3 | PASS ×3 | 251.7 | 394 | 431 ⚠ | 501 ⚠ |
| pessimistic | 5899 | 5899 | 0 | 0 | 0 | PASS ×3 | PASS ×3 | 193.6 | 512 | 632 ⚠ | 765 |
| optimistic | 5253 | 1887 | 0 | 3414 | 0 | PASS ×3 | PASS ×3 | 173.1 | 574 | 789 | 866 |
| redisson | 3164 | 3164 | 0 | 0 | 0 | PASS ×3 | PASS ×3 | 102.5 | 961 | 1499 ⚠ | 1588 ⚠ |

- RPS는 차감 구간(setup이 끝난 뒤부터 teardown 시작 전까지, 약 30.3~30.9초) 동안 처리한 요청 수를 그 시간으로 나눈 값이다.
- none은 7501건이 성공했지만 실제로 줄어든 재고는 751개(100000 − 99249)뿐이다. 3회 값은 성공 8040/7456/7501, 실제 차감 804/746/751이다.
- optimistic에서 503 비율은 3회 각각 65.0% / 63.8% / 65.8%다.
- 연결 실패를 포함한 "그 외"는 30번 실행 전체에서 0건이었다.

판정과 응답 개수(성공/409/503)는 3회 사이 차이가 11% 이하였다. 30% 이상 흔들린 항목은 모두 응답 시간과 RPS다.

- 예열은 atomic A로만 했다. 그래서 나머지 방식의 코드 경로는 1회차가 처음 실행이다. 1회차가 느린 이유가 이 때문인지는 확인하지 않았다.

## 트러블슈팅

### 시나리오 A에서 연결 거부 (connection refused)

**증상**
- 시나리오 A를 실행하면 차감 요청 일부가 서버에 닿지 못하고 실패했다. k6 로그: `dial tcp 127.0.0.1:8080: connectex: No connection could be made because the target machine actively refused it.`
- 스크립트는 이 요청을 "그 외 (연결 실패)"로 센다. 재고 판정에는 영향이 없지만, 실제로 재고를 두고 다툰 요청 수가 방식마다 달라져 비교 조건이 깨진다.
- 발생 기록 (`accept-count` 기본값 100일 때):
  - 앱을 띄운 직후 첫 A 실행: 62/200, 49/200
  - 예열을 마친 뒤에도 발생: none A 76/200, redisson A 54/200
  - 같은 조건의 다른 A 실행과 모든 B 실행에서는 0건
  - 실행할 때마다 나오는 게 아니라 간헐적으로 나왔다.

**원인 추정** (직접 확인하지는 않았다)
- Tomcat의 연결 대기열(`server.tomcat.accept-count`)은 기본값이 100이다. 시나리오 A는 VU 200명이 동시에 연결을 연다.
- 서버가 그 순간 연결을 충분히 빨리 받아 주지 못하면 대기열이 넘친다. Linux는 넘친 연결 요청을 버리고 클라이언트가 다시 시도하게 하지만, Windows는 바로 거절(RST)한다.
- 간헐적으로만 나오는 것도, 그 순간 서버가 얼마나 바쁜지(JVM 워밍업, GC, 같은 기기에서 도는 k6의 CPU 사용)에 따라 대기열이 넘치기도 하고 안 넘치기도 하기 때문으로 본다.
- 대기열이 실제로 얼마나 찼는지는 측정하지 않았다. 다만 정황이 이 추정과 맞는다.
  - 동시 연결이 100개인 B에서는 한 번도 나오지 않았다.
  - 아래 조치 뒤에는 사라졌다.

**조치**
- `src/main/resources/application.yml`에 `server.tomcat.accept-count: 1000`을 넣었다. 주석에 이유를 적어 두었다.
- 확인 결과
  - 앱을 재시작하고 atomic A를 3번 실행했다. 앱을 띄운 직후의 첫 실행을 포함해 연결 실패는 모두 0건이었다.
  - 이후 측정 30번에서도 0건이었다.
- 기본값으로 측정했던 1바퀴 결과는 비교 조건이 달라 버리고, 예열부터 다시 측정했다.
